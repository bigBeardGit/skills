## 一、代码规范哲学

### 1.1 核心共识

九本书虽然角度不同，但达成了以下共识：

**《编写可读代码的艺术》提出可读性基本定理**：
> 代码的写法应当使别人理解它所需的时间最小化。

**《代码整洁之道》提出**：
> 代码是写给人看的，只是偶尔在机器上执行。

**《代码大全》强调**：
> 软件构建远不止编码，它涵盖了详细设计、编码、调试、测试集成、可读性与长期维护。编程首先是与人交流，其次才是与计算机交流。

**《人月神话》的启示**：
> 概念完整性是系统设计中最重要的考虑因素。一个整洁、一致的编程风格本身就是概念完整性在代码层面的体现。

**《程序员修炼之道》的务实哲学**：
> DRY（不要重复自己）+ 正交性（减少组件间耦合）= 高内聚、低耦合的系统。

## 二、命名规范（Naming）

> **《Clean Code》**：命名是编程中最难的两件事之一。如果你发现改名很难，说明代码设计有问题。
>
> **《编写可读代码的艺术》**：把信息装到名字里，选择专业的词，避免泛泛的名字。名字应当尽可能精确。

### 2.1 通用命名原则

**原则一：名副其实**
- 名字应该回答所有重要问题：为什么存在、做什么事、怎么用
- 反例：`int d; // 已过去的天数` → 正例：`int elapsedDays;`
- 反例：`List accountList;`（实际是普通数组）→ 正例：`List accounts;`

**原则二：避免误导**
- 不要使用类型名做变量名（如 `accountList` 实际不是 List 类型）
- 不要使用外形相似的名字（如 `XYZControllerForEfficientHandlingOfStrings` vs `XYZControllerForEfficientStorageOfStrings`）
- 布尔变量不要加 `is` 前缀（阿里手册：POJO 布尔类型避免 `isDeleted`，框架序列化可能出错）

**原则三：做有意义的区分**
- 反例：`ProductInfo`、`ProductData` —— 区分没有意义
- 反例：`a1`、`a2`、`a3` —— 无法提供正确信息
- 反例：`getActiveAccount()`、`getActiveAccounts()`、`getActiveAccountInfo()` —— 读者知道该调用哪个吗？

**原则四：使用读得出来的名字**
- 反例：`genymdhms`（生成日期，年月日时分秒）→ 正例：`generationTimestamp`
- 反例：`modymdhms` → 正例：`modificationTimestamp`

**原则五：使用可搜索的名字**
- 单字母名称和数字常量难以搜索
- 反例：`for (int j = 0; j < 34; j++) { s += (t[j] * 4) / 5; }`
- 正例：`const int WORK_DAYS_PER_WEEK = 5; ... realDaysPerIdealDay * WORK_DAYS_PER_WEEK;`

**原则六：名字长度与作用域匹配**
- 《编写可读代码的艺术》：短名字适合小作用域（循环变量 `i`），长名字适合大作用域（全局配置 `maxConnectionsPerServer`）
- 《代码大全》：循环变量如果嵌套多层，用 `teamIndex`、`eventIndex` 比 `i`、`j` 更清晰

### 2.2 Java 命名规范（阿里巴巴 + Clean Code 融合）

| 类型 | 规范 | 正例 | 反例 |
|------|------|------|------|
| **类名** | UpperCamelCase，名词 | `UserService`、`OrderDetail` | `userService`、`order_detail` |
| **接口名** | UpperCamelCase，形容词用 -able | `Translatable`、`Serializable` | — |
| **方法名** | lowerCamelCase，动词/动宾 | `getUserById`、`saveOrder` | `GetUserById`、`save_order` |
| **变量名** | lowerCamelCase，名词 | `localValue`、`orderList` | `local_value`、`order_list` |
| **常量名** | 全大写，下划线分隔 | `MAX_STOCK_COUNT` | `maxStockCount`、`MAXSTOCKCOUNT` |
| **抽象类** | Abstract/Base 开头 | `AbstractUserService` | — |
| **异常类** | Exception 结尾 | `BusinessException` | — |
| **测试类** | 被测类名 + Test | `UserServiceTest` | — |
| **包名** | 全小写，单数 | `com.example.order` | `com.example.orders` |
| **枚举** | Enum 后缀，成员全大写 | `DealStatusEnum.SUCCESS` | `DealStatus.success` |

### 2.3 方法命名最佳实践

**《Clean Code》建议**：
- 方法名应当是动词或动词短语：`postPayment`、`deletePage`、`save`
- 访问器（Accessor）：`getXxx`、`setXxx`、`isXxx`
- 修改器（Mutator）：前缀用 `change`、`modify`、`update`、`set`
- 查询器（Query）：前缀用 `find`、`search`、`query`、`select`
- 删除器：前缀用 `delete`、`remove`、`drop`
- 转换器：`toXxx`（如 `toString()`）、`asXxx`（如 `asList()`）、`parseXxx`

**《Effective Java》第68条**：遵守普遍接受的命名惯例。

## 三、函数/方法规范（Functions）

> **《Clean Code》**：函数应该短小。函数应该只做一件事。函数应该做好一件事。
>
> **《代码大全》**：子程序应保持短小。子程序的参数个数限制在大约7个以内。

### 3.1 函数长度

- **《Clean Code》**：理想的函数长度不超过20行，尽量控制在10行以内
- **《代码大全》**：子程序长度有序地增长到100-200行是可以接受的，但超过200行需要非常小心
- **《阿里手册》**：单个方法的总行数不超过80行
- **统一建议**：Java 方法尽量控制在50行以内，超过则考虑拆分

### 3.2 函数只做一件事

**判断标准**（《Clean Code》）：
- 如果一个函数只是做了该函数名下同一抽象层上的步骤，则函数只做了一件事
- 反例：一个函数既验证用户、又格式化名字、又检查权限、又保存数据、又发送通知
- 正例：`processUser()` → 调用 `validateUser()`、`formatFullName()`、`checkPermission()`、`saveUserData()`、`sendUpdateNotification()`

### 3.3 函数参数

**《Clean Code》**：
- 最理想的参数数量是零，其次是1个，再次是2个，应尽量避免3个及以上参数
- 参数多于3个时，考虑封装为对象
- 不要使用标识参数（flag 参数），如 `render(boolean isSuite)`，应拆分为 `renderForSuite()` 和 `renderForSingleTest()`

**《Effective Java》第49条**：
- 检查参数的有效性，在方法体开始处用 `Objects.requireNonNull()` 等进行检查
- 对于非公有的方法，可以使用断言（assert）来检查参数

**《阿里手册》**：
- 方法参数避免用 `Map` 传递业务对象，应使用 DTO
- 方法的返回值如果是集合，不允许返回 `null`，应返回空集合

### 3.4 避免副作用

**《Clean Code》**：
- 函数承诺做一件事，但还做了其他隐藏的事，就是副作用
- 反例：`checkPassword()` 除了检查密码，还初始化了 Session
- 正例：`checkPassword()` 只检查密码，`initializeSession()` 单独做初始化

### 3.5 使用异常替代返回错误码

**《Clean Code》**：
- 返回错误码会迫使调用者立刻处理错误，导致深层嵌套
- 使用异常可以将错误处理代码从主路径中分离

**《Effective Java》第69、70、72条**：
- 只在异常情况下使用异常，不要用于正常控制流
- 对可恢复的情况使用受检异常，对编程错误使用运行时异常
- 优先使用标准的异常（如 `IllegalArgumentException`、`IllegalStateException`）
- 不要忽略异常（空的 catch 块是代码的毒瘤）

## 四、类与面向对象规范（Classes & OOP）

> **《Clean Code》**：类应该短小。类的名称应当描述其职责。如果无法为类找到一个精确的名称，这个类可能就太长了。
>
> **《Effective Java》**：类和接口是Java程序设计语言的核心，它们是我们语言的基本单元。

### 4.1 类的组织

**《Clean Code》建议的类组织顺序**：
1. 公共静态常量
2. 私有静态变量
3. 私有实例变量
4. 公共方法（调用私有工具的公共方法在前，私有工具方法在后）

**《阿里手册》**：
- 不同逻辑、不同语义、不同业务的代码之间插入一个空行分隔
- 禁止在类中声明 `public` 或 `protected` 的字段，应通过 getter/setter 访问

### 4.2 类的规模

- **《Clean Code》》：类应该足够短小，权责明确
- **《代码大全》》：警惕拥有超过约7个数据成员的类
- **统一建议**：类的总行数不超过500行，方法数不超过20个。如果一个类过大，考虑按职责拆分

### 4.3 封装与访问控制

**《Effective Java》第15条**：使类和成员的可访问性最小化。
- 尽可能使每个类或成员不被外界访问
- 对于成员（字段、方法、嵌套类），访问权限应尽可能为 `private`
- 需要包内访问的用 `default`，需要子类访问的用 `protected`，公开的才用 `public`

**《Effective Java》第16条**：要在公有类而非公有域中使用访问方法。
- 反例：公有类的实例域不应直接暴露（`public String name;`）
- 正例：使用 `private` 字段 + `public` getter/setter

**例外**：不可变类可以暴露公有 final 字段（如 `Point` 类的 `x` 和 `y`）。

### 4.4 不可变对象

**《Effective Java》第17条**：使可变性最小化。
- 不可变对象本质上是线程安全的，不需要同步
- 不可变对象可以被自由地共享，可以重用已有实例
- 不可变对象为其他对象提供了大量的构建块
- 设计类时，除非有很好的理由让类可变，否则应设为不可变

### 4.5 继承与组合

**《Effective Java》第18条**：复合优先于继承。
- 继承打破了封装，子类依赖于父类的实现细节
- 父类的变化可能导致子类的异常行为
- 正例：使用组合 + 转发（Forwarding）替代继承

### 4.6 接口与抽象类

**《Effective Java》第20条**：接口优先于抽象类。
- 接口允许构造非层次结构的类型框架
- 接口是定义 mixin（混合类型）的理想选择
- 接口允许安全地增强类的功能（包装器模式）
- 抽象类可以作为骨架实现（Skeletal Implementation），与接口配合

## 五、注释与文档规范（Comments）

> **《Clean Code》**：注释的恰当用法是弥补我们在用代码表达意图时遭遇的失败。注释不能美化糟糕的代码。
>
> **《编写可读代码的艺术》**：注释的目的是尽量帮助读者了解得和作者一样多。注释应当说明"做什么""为什么"而不是"怎么做"。

### 5.1 好注释 vs 坏注释

**好注释**（《Clean Code》）：
1. **法律信息**：版权、许可证声明
2. **信息性注释**：提供基本信息（如返回某个抽象类型的具体实现）
3. **对意图的解释**：解释为什么这么做
4. **警示**：警告会产生某种后果（如 `// 测试运行时间较长`）
5. **TODO 注释**：标记待完成的工作
6. **放大**：放大某种看似不合理之事的重要性

**坏注释**：
1. **喃喃自语**：作者自己才明白的注释
2. **多余的注释**：代码本身已能清晰表达，无需注释
3. **误导性注释**：注释与代码不符
4. **循规式注释**：每个函数都加 Javadoc，不管是否需要
5. **日志式注释**：记录每次修改历史（用版本控制替代）
6. **废话注释**：`// 构造函数`、`// 天呐`
7. **括号后面的注释**：标记结束括号（如 `} // try`、`} // if`），说明嵌套太深
8. **归属与署名**：`// 张三添加`（用版本控制替代）

### 5.2 Javadoc 规范

**《阿里手册》**：
- 类、类属性、类方法的注释必须使用 Javadoc 规范，使用 `/** 内容 */` 格式
- 方法注释应包含：方法说明、参数说明（`@param`）、返回值（`@return`）、异常（`@throws`）
- 所有的抽象方法必须用 Javadoc 注释

**示例**：
```java
/**
 * 根据用户ID查询用户信息。
 *
 * @param userId 用户ID，不能为空
 * @return 用户信息，如果用户不存在则返回null
 * @throws IllegalArgumentException 如果userId为空
 */
public User getUserById(Long userId) {
    // ...
}
```

### 5.3 注释格式

**《编写可读代码的艺术》**：
- 注释应紧凑，避免冗长
- 避免使用不明确的代词（如 `it`、`this`）
- 精确描述函数的行为，包括边界条件
- 用输入/输出例子说明特别的情况
- 采用信息含量高的词

## 六、格式与风格规范（Formatting）

> **《Clean Code》**：代码格式关乎沟通，沟通是专业开发者的首要职责。
>
> **《代码大全》**：好的代码布局应凸显程序的逻辑结构，使代码易于阅读、理解、检查及修改。

### 6.1 垂直格式

**《Clean Code》建议**：
- 源文件像报纸文章：名称简单且一目了然，最前面给出高层次概念和算法，细节往下逐次展开
- 概念相关的代码应该放在一起，相关性越强，距离越近
- 不同逻辑之间用空行分隔

**《阿里手册》**：
- 单行字符数不超过120个，超出需要换行
- 换行时第二行相对第一行缩进4个空格
- 方法体内的执行语句组、变量的定义语句组、不同的业务逻辑之间插入一个空行

### 6.2 水平格式

**《Clean Code》**：
- 使用缩进体现层级关系
- 赋值语句左右对齐（如果有助于可读性）
- 团队应达成一致的风格，然后每个人都应遵循

**《阿里手册》**：
- 使用4个空格缩进，禁止使用Tab
- 左小括号和字符之间不出现空格；右小括号和字符之间也不出现空格
- `if`/`for`/`while`/`switch`/`do` 等保留字与左右括号之间都必须加空格
- 任何运算符左右必须加一个空格

### 6.3 大括号风格

**《阿里手册》推荐**：
```java
if (condition) {
    // ...
} else {
    // ...
}
```

**《代码大全》**：每个专业的程序员都能毫无困难地阅读以上任何一种风格的代码，但一定要保持一致。

## 七、错误处理与防御式编程（Error Handling & Defensive Programming）

> **《代码大全》**：防御式编程的核心思想是：子程序应该不因传入错误数据而被破坏，哪怕是由其他子程序产生的错误数据。
>
> **《Effective Java》**：异常应该只用于异常的情况，永远不应该用在正常的控制流中。

### 7.1 异常使用规范

**《Effective Java》核心原则**：
- 第69条：只在异常情况下使用异常。不要用异常来做正常的流程控制
- 第70条：对可恢复的情况使用受检异常，对编程错误使用运行时异常
- 第71条：避免不必要地使用受检异常（如果调用者不大可能恢复，用运行时异常）
- 第72条：优先使用标准的异常（`IllegalArgumentException`、`IllegalStateException`、`NullPointerException`、`IndexOutOfBoundsException` 等）
- 第73条：抛出与抽象相对应的异常（高层方法应捕获低层异常并抛出高层异常）
- 第74条：每个方法抛出的异常都要有文档
- 第77条：不要忽略异常

**《阿里手册》**：
- Java 类库中定义的可以通过预检查方式规避的 RuntimeException 异常不应该通过 catch 的方式来处理
- 异常不要用来做流程控制、条件控制
- catch 时请分清稳定代码和非稳定代码，稳定代码指的是无论如何不会出错的代码
- 捕获异常是为了处理它，不要捕获了却什么都不处理（至少打印日志）

### 7.2 空值处理

**《Effective Java》第54条**：返回零长度的数组或集合，而不是 null。
- 返回 null 会迫使调用者做额外的 null 检查，增加出错概率
- 正例：`return Collections.emptyList();`

**《阿里手册》**：
- 方法的返回值可以为 null，不强制返回空集合或空对象，但必须添加注释说明什么情况下会返回 null
- 防止 NPE 是程序员的基本修养

**Java 8+ 最佳实践**：
- 使用 `Optional` 作为可能为空的返回值类型
- 方法参数中避免使用 `Optional`
- 使用 `Optional.ofNullable()` 和 `orElse()`/`orElseGet()`/`orElseThrow()`

### 7.3 断言与前置条件检查

**《Effective Java》第49条**：检查参数的有效性。
- 对于公有的方法，使用 `Objects.requireNonNull()` 检查 null
- 对于非公有的方法，可以使用断言（assert）
- 对于计算密集型检查，在检查前使用文档说明

**《代码大全》防御式编程清单**：
- 检查所有来源于外部的数据的值
- 检查子程序所有输入参数的值
- 决定如何处理错误的输入数据

### 7.4 日志规范

**《Clean Code》**：
- 日志是系统运行时的"黑匣子"，好的日志应提供足够的信息进行故障排查

**《阿里手册》**：
- 使用 SLF4J/Logback，不要直接使用 `System.out.println`
- 日志级别：ERROR（需要处理）、WARN（关注但可继续）、INFO（关键流程）、DEBUG（开发调试）
- 不要打印敏感信息（密码、身份证号、银行卡号）
- 异常日志：`log.error("xxx failed, userId={}", userId, e)`，保留完整堆栈
- 生产环境禁止输出 debug 日志；有选择地输出 info 日志；如果使用 warn 来记录刚上线时的业务行为信息，一定要注意日志输出量的问题

## 八、并发编程规范（Concurrency）

> **《Effective Java》第78-84条**：并发编程很困难，容易出错。最好避免共享可变状态。
>
> **《代码大全》**：对于多线程编程，你需要有比对付蓝宝石还要更小心的心态。

### 8.1 基本原则

**《Effective Java》第78条**：同步访问共享的可变数据。
- `synchronized` 关键字可以保证原子性和可见性
- 读操作和写操作都需要同步
- 避免过度同步（导致性能问题和死锁）

**《Effective Java》第79条**：避免过度同步。
- 不要在同步区域内调用外来方法（alien method），会导致死锁和性能问题
- 尽量将同步范围限制到最小

**《Effective Java》第83条**：慎用延迟初始化。
- 大多数情况下，正常的初始化要优于延迟初始化
- 如果必须使用延迟初始化，对于实例字段使用双重检查模式（DCL），对于静态字段使用 `lazy initialization holder class` 模式

### 8.2 线程安全

**《阿里手册》**：
- 创建线程或线程池时请指定有意义的线程名称，方便出错时回溯
- 线程资源必须通过线程池提供，不允许在应用中自行显式创建线程
- 线程池不允许使用 `Executors` 去创建，而是通过 `ThreadPoolExecutor` 的方式，这样的处理方式让写的同学更加明确线程池的运行规则，规避资源耗尽的风险
- `SimpleDateFormat` 是线程不安全的类，一般不要定义为 static 变量，如果定义为 static，必须加锁，或使用 `DateUtils` 工具类
- 高并发时，同步调用应该去考量锁的性能损耗。能用无锁数据结构，就不要用锁；能锁区块，就不要锁整个方法体；能用对象锁，就不要用类锁

### 8.3 并发集合与工具

**《Effective Java》第81条**：并发工具优先于 `wait` 和 `notify`。
- 使用 `java.util.concurrent` 包中的高级并发工具
- `ConcurrentHashMap` 优于 `Collections.synchronizedMap`
- `BlockingQueue` 用于生产者-消费者模式
- `CountDownLatch`、`CyclicBarrier`、`Semaphore` 用于同步

## 九、集合与泛型规范（Collections & Generics）

> **《Effective Java》第26-33条**：请不要使用原生类型（raw type）。

### 9.1 泛型使用

**《Effective Java》核心原则**：
- 第26条：不要使用原生类型。使用 `List<String>` 而不是 `List`
- 第27条：消除非受检警告。尽量在编译时消除所有警告
- 第28条：列表优于数组。数组是协变的、可具体化的；泛型是不可变的、可擦除的
- 第29条：优先考虑类型安全的异构容器

### 9.2 集合使用规范

**《阿里手册》**：
- 关于 `hashCode` 和 `equals` 的处理，遵循如下规则：
  - 只要重写 `equals`，就必须重写 `hashCode`
  - `Set` 存储的是不重复的对象，依据 `hashCode` 和 `equals` 进行判断，所以 `Set` 存储的对象必须重写这两个方法
  - 如果自定义对象作为 `Map` 的键，那么必须重写 `hashCode` 和 `equals`
- `ArrayList` 的 `subList` 结果不可强转成 `ArrayList`
- 使用集合转数组的方法，必须使用集合的 `toArray(T[] array)`，传入的是类型完全一样的数组
- 使用工具类 `Arrays.asList()` 把数组转换成集合时，不能使用其修改集合相关的方法（`add`/`remove`/`clear`）
- 泛型通配符 `<? extends T>` 来接收返回的数据，此写法的泛型集合不能使用 `add` 方法，而 `<? super T>` 不能使用 `get` 方法
- 不要在 `foreach` 循环里进行元素的 `remove`/`add` 操作，`remove` 元素请使用 `Iterator` 方式
- 集合初始化时，指定集合初始值大小

### 9.3 equals 和 hashCode

**《Effective Java》第10、11条**：
- 重写 `equals` 方法时遵守通用约定：自反性、对称性、传递性、一致性、非空性
- 重写 `equals` 时总要重写 `hashCode`
- `hashCode` 的关键域应参与计算，使用 `31 * result + fieldHashCode` 的公式
- 不要依赖 `equals` 比较 `URL` 对象（网络访问可能导致阻塞）

## 十、重构与代码质量（Refactoring）

> **《重构》**：重构是对软件内部结构的一种调整，目的是在不改变软件可观察行为的前提下，提高其可理解性，降低其修改成本。
>
> **《程序员修炼之道》**：不要容忍破窗户。看到糟糕的设计、错误的决策、低劣的代码，不要只是看看，应该马上修正。

### 10.1 代码坏味道速查表

| 坏味道 | 症状 | 重构手法 |
|--------|------|----------|
| **重复代码** | 相同或相似的代码出现在多处 | 提炼方法（Extract Method） |
| **过长方法** | 方法超过50行，做了多件事 | 提炼方法、以查询取代临时变量 |
| **过大类** | 类超过500行，职责过多 | 提炼类、提炼子类 |
| **过长参数列表** | 参数超过3-4个 | 引入参数对象、保持对象完整 |
| **发散式变化** | 一个类受多种变化的影响 | 拆分责任到不同类 |
| **霰弹式修改** | 一种变化引发多个类修改 | 搬移方法/字段到同一类 |
| **依恋情结** | 方法对另一个类的兴趣超过自己 | 搬移方法 |
| **数据泥团** | 多个类中相同的一组数据 | 提炼类 |
| **基本类型偏执** | 用基本类型代替小对象 | 以对象取代基本类型 |
| **Switch 惊悚现身** | 多处使用 switch/if-else 处理类型 | 以多态取代条件表达式 |
| **平行继承体系** | 为一个类添加子类时必须为另一个类添加 | 让继承体系的一个实例引用另一个 |
| **冗赘类** | 类不做任何事情 | 内联类 |
| **夸夸其谈通用性** | 过度设计，预留不存在的功能 | 折叠继承体系、内联类 |
| **临时字段** | 对象中某些字段只在特定情况下使用 | 提炼类 |
| **过长消息链** | `a.getB().getC().getD()` | 隐藏委托、提炼方法 |
| **中间人** | 类接口有一半都委托给其他类 | 移除中间人、内联方法 |
| **狎昵关系** | 两个类过于亲密，访问私有成员 | 搬移方法/字段、将双向关联改为单向 |
| **异曲同工的类** | 两个类做相同的事，接口不同 | 重命名方法、提炼超类 |
| **纯数据类** | 只有字段和 getter/setter | 封装集合、以对象取代基本类型 |
| **被拒绝的遗赠** | 子类继承不需要的方法 | 以委托取代继承 |
| **过多的注释** | 需要大量注释来解释代码 | 用方法名解释意图、重构代码 |

### 10.2 重构原则

**《重构》核心原则**：
1. **小步前进**：每次只做一点点改动
2. **频繁测试**：重构前后都要运行测试，确保行为不变
3. **代码坏味道是重构的信号**：闻到坏味道就应该重构
4. **重构与设计的关系**：重构可以弥补设计的不足，但好的设计可以减少重构的需要

**《代码大全》重构时机**：
- 添加功能时重构
- 修复错误时重构
- 代码审查时重构

### 10.3 破窗理论

**《程序员修炼之道》**：
- 不要容忍破窗户（糟糕的代码、糟糕的决策）
- 看到糟糕的代码，马上修正；如果没时间，至少标记 TODO/FIXME
- 一个项目中如果有太多"破窗"，会传递出"质量不重要"的信号，导致整个系统迅速恶化

## 十一、测试规范（Testing）

> **《代码整洁之道》**：测试代码和生产代码一样重要。它需要被思考、被设计，并且它必须像生产代码一样保持整洁。
>
> **《程序员修炼之道》**：早测试、常测试、自动测试。自动化测试是程序员最好的朋友。

### 11.1 单元测试原则（F.I.R.S.T.）

**《Clean Code》提出的 FIRST 原则**：
- **F**ast（快速）：测试应该能快速运行
- **I**ndependent（独立）：测试之间不应相互依赖
- **R**epeatable（可重复）：测试在任何环境下都应能重复运行
- **S**elf-Validating（自验证）：测试应该有布尔输出（通过/失败）
- **T**imely（及时）：测试应在生产代码之前编写（TDD）

### 11.2 测试代码规范

**《Clean Code》**：
- 测试代码和生产代码一样需要保持整洁
- 一个测试只做一件事，只断言一个概念
- 使用有意义的测试名称，如 `methodName_should_expectedBehavior_when_scenario`

**《阿里手册》**：
- 好的单元测试必须遵守 AIR 原则：
  - **A**utomatic（自动化）：单元测试应该是全自动执行的，并且非交互式的
  - **I**ndependent（独立性）：单元测试用例之间决不能互相调用，也不能依赖执行的先后次序
  - **R**epeatable（可重复）：单元测试是可以重复执行的，不能受到外界环境的影响
- 单元测试应该是可重复执行的，不能依赖外部数据或状态
- 单元测试需要是确定性的，同样的输入必须产生同样的输出
- 单元测试代码必须写在如下工程目录：`src/test/java`，不允许写在业务代码目录下

### 11.3 测试覆盖率

**《代码大全》**：
- 测试套件应测试所有可能出错的地方
- 只要还有未被测试覆盖的条件或未被验证的计算，测试就是不充分的
- 不要跳过编写简单的测试，因为它们的文档价值高于编写成本
- 要特别注意测试边界条件

**《阿里手册》**：
- 单元测试的粒度应该足够小，细化到被测方法的级别
- 核心业务、核心应用、核心模块的增量代码确保单元测试通过
- 单元测试代码必须能够重复执行，不能依赖于外部数据或状态

## 十二、工程结构与项目规范

### 12.1 应用分层（阿里手册）

推荐分层结构：
```
├── controller/        # 控制层，处理 HTTP 请求
├── service/           # 业务逻辑层
│   ├── impl/          # 业务实现
├── mapper/dao/        # 数据访问层
├── domain/entity/     # 领域模型/实体
├── dto/               # 数据传输对象
├── vo/                # 视图对象
├── util/              # 工具类
├── config/            # 配置类
└── enums/             # 枚举
```

### 12.2 常量定义规范

**《阿里手册》**：
- 不允许出现任何魔法值（即未经定义的常量）直接出现在代码中
- 不要使用一个常量类维护所有常量，要按常量功能进行归类，分开维护
- 常量的复用层次有五层：跨应用共享常量、应用内共享常量、子工程内共享常量、包内共享常量、类内共享常量
- 如果变量值仅在一个范围内变化，用 `Enum` 类

### 12.3 二方库依赖

**《阿里手册》**：
- 定义 GAV（GroupID、ArtifactID、Version）规则
- 线上应用不要依赖 SNAPSHOT 版本
- 二方库的新增或升级，应保持除功能点之外的其他 jar 包仲裁结果不变

## 十三、职业素养与团队协作

> **《程序员职业素养》**：专业主义意味着承担责任。专业人士不找借口。
>
> **《人月神话》**：向进度落后的项目中增加人手，只会使进度更加落后（Brooks法则）。

### 13.1 承诺管理

**《Clean Coder》**：
- 专业人士知道自己能够承诺什么，并坚守承诺
- 如果你无法做出承诺，就不要做；如果承诺了，就必须兑现
- 说"不"是专业人士的权利和义务。当需求不合理、时间不够时，要勇敢说"不"
- 说"是"意味着全力以赴。不要轻易说"是"，除非你真的能做到

### 13.2 时间管理

**《Clean Coder》**：
- 番茄工作法：25分钟专注 + 5分钟休息
- 区分优先级：紧急且重要 > 重要不紧急 > 紧急不重要 > 不紧急不重要
- 避免会议黑洞：不必要的会议是时间杀手

### 13.3 压力管理

**《Clean Coder》**：
- 压力下保持冷静，不要惊慌失措
- 不要牺牲代码质量来赶进度（破窗理论）
- 如果确实无法按时完成，提前沟通，不要拖到最后一刻

### 13.4 团队协作

**《人月神话》**：
- **Brooks法则**：向进度落后的项目中增加人手，只会使进度更加落后
- **概念完整性**：系统的设计应当有一个或少数几个设计者来保证统一性和一致性
- **外科手术队伍**：首席程序员 + 协助人员，减少沟通成本

**《Pragmatic Programmer》**：
- **DRY**：不要重复自己。每段知识在系统中必须有单一、明确、权威的表示
- **正交性**：消除一个事物对不相关事物的影响。修改一处不应导致其他地方出错
- **可逆性**：没有最终决定。确保反转决定的成本低廉
- **曳光弹**：快速构建可工作的系统框架，然后逐步完善
- **估算**：养成估算的习惯，避免意外

### 13.5 持续学习

**《Pragmatic Programmer》**：
- 每年至少学习一种新语言
- 每季度阅读一本技术书籍
- 也要阅读非技术书籍
- 参加技术会议、加入技术社区
- 持续学习是程序员的核心竞争力

## 十四、代码审查清单（Code Review Checklist）

综合九本书的观点，代码审查时按以下维度检查：

### 14.1 可读性
- [ ] 命名是否名副其实、读得出来、可搜索？
- [ ] 方法是否短小、只做一件事？
- [ ] 类是否职责单一、规模合理？
- [ ] 注释是否解释了"为什么"而非"做什么"？
- [ ] 格式是否一致、符合团队规范？

### 14.2 健壮性
- [ ] 是否检查了参数有效性？
- [ ] 是否处理了所有异常路径？
- [ ] 是否有空指针风险？
- [ ] 并发代码是否线程安全？
- [ ] 资源是否正确释放（try-with-resources）？

### 14.3 设计质量
- [ ] 是否遵循 SOLID 原则？
- [ ] 是否重复了已有代码（DRY）？
- [ ] 修改此处是否会影响不相关的地方（正交性）？
- [ ] 是否使用了合适的设计模式？
- [ ] 依赖关系是否合理（DIP）？

### 14.4 性能
- [ ] 是否有不必要的对象创建？
- [ ] 集合是否指定了初始容量？
- [ ] 是否有循环查库/循环调用外部接口？
- [ ] 日志输出是否会影响性能？

### 14.5 安全
- [ ] 是否有 SQL 注入风险？
- [ ] 是否有 XSS 风险？
- [ ] 敏感数据是否脱敏？
- [ ] 是否有越权访问风险？

### 14.6 测试
- [ ] 是否有对应的单元测试？
- [ ] 测试是否覆盖了边界条件？
- [ ] 测试是否独立、可重复？
- [ ] 是否测试了异常路径？
