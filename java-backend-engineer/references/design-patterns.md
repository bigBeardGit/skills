# 设计模式深度参考

> 综合《设计模式：可复用面向对象软件的基础》(GOF)、《Head First 设计模式》、《图解设计模式》、《设计模式之禅》、《大话设计模式》、《研磨设计模式》、《深入设计模式》七本经典著作的核心思想。

---

## 一、设计模式哲学

### 1.1 本质定义

GOF 定义：**设计模式是在特定环境下，针对一类设计问题的可复用解决方案。**

《大话设计模式》补充：设计模式是前辈们对代码开发经验的总结，是一套提高代码**可复用性、可读性、可维护性、稳健性、安全性**的解决方案。

《研磨设计模式》强调：**设计原则是思想层面的指导，设计模式是实现层面的手段。** 模式是原则的具体体现，原则是模式的灵魂。

### 1.2 两大核心设计原则（GOF 基石）

> 这两条原则是 GOF 全书反复出现的主题，也是《Head First》开篇强调的"九大 OO 原则"之首。

**原则一：针对接口编程，而不是针对实现编程**
- 不将变量声明为某个具体类的实例，而是让它遵从抽象类/接口定义的契约
- 客户无需知道对象的特定类型，只需知道它所期望的接口
- 客户无需知道对象用什么类实现，只需知道定义接口的抽象类
- **这是实现松耦合的关键，也是多态的根基**

**原则二：多用组合，少用继承**
- 继承是白箱复用，父类实现细节暴露给子类，耦合过强
- 组合是黑箱复用，被包含对象的内部细节对外不可见
- 继承在编译时静态确定，组合在运行时动态绑定，更灵活
- 《Head First》："继承虽然强大，但不总是最灵活的设计方式"

### 1.3 设计模式的四要素（GOF 框架）

每个模式都应从四个维度理解：
1. **模式名称**：创建通用词汇，让团队沟通更高效
2. **问题**：描述模式应用的场景和要解决的问题
3. **解决方案**：抽象的类/对象结构描述，不绑定具体实现
4. **效果**：使用模式的优缺点、权衡取舍

### 1.4 学习设计模式的正确姿势

《研磨设计模式》：学习设计模式不在于死记硬背，而在于**更深刻地理解面向对象，打开新的思维方式，体验经典设计之美**。

《Head First》：先理解设计原则（为什么），再学习设计模式（怎么做）。**原则是道，模式是术**。

《设计模式之禅》：用历史典故和生活案例理解模式的**核心思想**，再映射到代码。

## 二、七大面向对象设计原则

### 2.1 单一职责原则 (SRP)

> **一个类应该仅有一个引起它变化的原因。**

- 《大话设计模式》：如果一个类承担的职责过多，就等于把这些职责耦合在一起，一个职责的变化可能会削弱或抑制这个类完成其他职责的能力
- 判断标准：如果能想到多于一个的动机去改变一个类，那么这个类就具有多于一个的职责
- 实践：分离业务逻辑和界面逻辑；将不同的职责拆分为不同的类或接口

### 2.2 开闭原则 (OCP) — 核心中的核心

> **软件实体应当对扩展开放，对修改关闭。**

- 《设计模式之禅》：面对需求，对程序的改动是通过**新增代码**进行的，而不是更改现有的代码
- 实现关键：**抽象化** —— 为系统定义一个一劳永逸、不再改变的抽象设计
- 《研磨设计模式》：OCP 是设计原则的核心目标，其他原则都是为 OCP 服务的
- 实践：用多态替换条件分支(if-else/switch)；定义抽象基类/接口，新功能通过新增子类实现

### 2.3 里氏替换原则 (LSP)

> **所有引用基类的地方必须能透明地使用其子类的对象。**

- 《大话设计模式》：软件实体如果使用的是一个父类的话，那么一定适用于其子类，而且察觉不出父类对象和子类对象的区别
- 核心要求：子类可以扩展父类的功能，但不能改变父类原有的功能
- 禁止行为：子类重写父类非抽象方法并改变其原有语义
- 经典反例：`Square extends Rectangle`（正方形改变长方形的 setWidth/setHeight 语义）
- 实践：继承应当确保子类型 IS-A 父类型，且行为一致

### 2.4 接口隔离原则 (ISP)

> **客户端不应该依赖它不需要的接口；一个类对另一个类的依赖应该建立在最小的接口上。**

- 《设计模式之禅》：建立单一接口，不要建立庞大臃肿的接口；接口中的方法尽量少，为各个类建立专用接口
- 本质：接口拆分，避免"胖接口"污染客户端
- 与 SRP 的区别：SRP 关注类的职责，ISP 关注接口的粒度
- 实践：将大接口拆分为多个小接口，客户端按需依赖

### 2.5 依赖倒置原则 (DIP)

> **高层模块不应该依赖低层模块，二者都应该依赖抽象；抽象不应该依赖细节，细节应该依赖抽象。**

- 《大话设计模式》：针对接口编程，不要针对实现编程
- 核心：通过抽象（接口/抽象类）解耦高层与低层
- 实现方式：构造函数注入、Setter 注入、接口注入（Spring IoC 的本质就是 DIP 的实践）
- 实践：模块间依赖终止于抽象，而非具体实现类

### 2.6 迪米特法则 / 最少知识原则 (LoD)

> **一个对象应当对其他对象有尽可能少的了解；如果两个类不必彼此直接通信，那么就不应当发生直接的相互作用。**

- 《大话设计模式》：根本思想是强调类之间的松耦合
- 核心：只与直接的朋友通信（成员变量、方法参数、方法返回值、局部变量）
- 反模式：链式调用 `a.getB().getC().doSomething()`
- 实践：通过外观模式或中介者减少类间耦合；信息隐藏

### 2.7 合成复用原则 / 组合聚合复用原则 (CARP)

> **尽量使用对象组合/聚合，而不是继承来达到复用的目的。**

- 《大话设计模式》：组合关系是强"拥有"关系（鸟和翅膀）；聚合关系是弱"拥有"关系（雁群和大雁）
- 继承的缺点：破坏封装，父类变化影响所有子类，编译时静态绑定
- 组合的优点：黑箱复用，运行时动态绑定，耦合度低
- 实践：优先使用 Has-A 关系，慎用 Is-A 关系

### 2.8 原则之间的关系

```
              开闭原则 (OCP) —— 终极目标
                     │
    ┌───────────────┼───────────────┐
    │               │               │
   SRP            LSP            DIP
 (基础)         (继承约束)      (依赖方向)
    │               │               │
    └───────────────┴───────────────┘
              ISP + LoD + CARP
           (接口粒度 + 知识隐藏 + 复用方式)
```

- **OCP 是总纲**，是架构设计的终极目标
- **SRP 是基础**，职责清晰才能谈扩展
- **LSP + DIP** 保证扩展时系统的正确性
- **ISP + LoD + CARP** 是具体的实现手段

## 三、23种设计模式详解

### 统一描述框架

每种模式按以下结构分析：
- **核心意图**：一句话概括模式的本质
- **适用场景**：什么时候用、解决什么问题
- **UML 结构**：角色和关系
- **Java 实现要点**：关键代码结构
- **相关模式对比**：易混淆模式的区别
- **实际应用**：JDK / Spring / 主流框架中的应用

---

### 3.1 创建型模式（Creational）

> 关注对象的创建机制，将对象的创建与使用分离。

#### 单例模式 (Singleton)

**核心意图**：确保一个类只有一个实例，并提供一个全局访问点。

**适用场景**：
- 需要全局唯一实例的场景（配置中心、连接池、线程池、缓存）
- 控制共享资源的访问（数据库连接、文件系统）

**Java 实现要点**：
```java
// 枚举方式（最佳，防反射/序列化破坏）
public enum Singleton {
    INSTANCE;
    public void doSomething() {}
}

// DCL + volatile（经典，需理解指令重排）
public class Singleton {
    private static volatile Singleton instance;
    private Singleton() { /* 防反射 */ if (instance != null) throw new RuntimeException(); }
    public static Singleton getInstance() {
        if (instance == null) {
            synchronized (Singleton.class) {
                if (instance == null) instance = new Singleton();
            }
        }
        return instance;
    }
    // 防序列化破坏
    private Object readResolve() { return getInstance(); }
}
```

**破坏方式与防御**：
- 反射 → 构造函数检查
- 序列化 → readResolve()
- 克隆 → 重写 clone() 抛异常

**实际应用**：`Runtime.getRuntime()`、`Spring Bean` 默认单例、`Enum` 本质就是单例

---

#### 工厂方法模式 (Factory Method)

**核心意图**：定义创建对象的接口，让子类决定实例化哪个类。将实例化延迟到子类。

**适用场景**：
- 创建对象需要大量重复代码
- 客户端不需要知道所创建对象的具体类
- 一个类通过其子类来指定创建哪个对象

**与简单工厂的区别**：
- 简单工厂：一个工厂类，通过 if-else/switch 判断创建哪种产品（不属于 GOF 23）
- 工厂方法：将工厂也抽象化，每个具体产品对应一个具体工厂

**实际应用**：Spring 的 `BeanFactory`、`Collection` 的 `iterator()` 方法

---

#### 抽象工厂模式 (Abstract Factory)

**核心意图**：创建相关或依赖对象的家族，而不需要明确指定具体类。

**适用场景**：
- 系统需要多系列产品（如 UI 组件库：Windows 风格 / Mac 风格）
- 需要保证产品族内对象的一致性

**与工厂方法的区别**：
- 工厂方法：创建一个产品，关注"单个对象的创建"
- 抽象工厂：创建一族产品，关注"产品族的创建"

**实际应用**：`ConnectionFactory`(不同数据库连接族)、Spring 的 `FactoryBean`

---

#### 建造者模式 (Builder)

**核心意图**：将一个复杂对象的构建与它的表示分离，使得同样的构建过程可以创建不同的表示。

**适用场景**：
- 对象构造参数过多（尤其多个可选参数）
- 对象的构造过程复杂，需要分步骤进行
- 需要创建不同表示的同类对象

**Java 实现**：链式调用 + 静态内部类
```java
public class Computer {
    private final String cpu;
    private final int ram;
    // ...
    private Computer(Builder builder) { this.cpu = builder.cpu; this.ram = builder.ram; }
    public static class Builder {
        private String cpu;
        private int ram;
        public Builder cpu(String cpu) { this.cpu = cpu; return this; }
        public Builder ram(int ram) { this.ram = ram; return this; }
        public Computer build() { return new Computer(this); }
    }
}
```

**实际应用**：`StringBuilder`、`OkHttpClient.Builder`、`Lombok @Builder`

**与工厂模式的区别**：
- 工厂：关注"创建什么对象"，一步完成
- 建造者：关注"如何一步步构建对象"，分步完成

---

#### 原型模式 (Prototype)

**核心意图**：用原型实例指定创建对象的种类，并通过复制这些原型创建新对象。

**适用场景**：
- 创建对象成本较大（如需要复杂计算或数据库查询）
- 对象状态需要复制，但不想通过构造函数重新构建

**Java 实现**：
- 浅拷贝：`clone()` —— 复制基本类型，引用类型共享
- 深拷贝：序列化、手动复制引用对象、JSON 转换

**实际应用**：`Object.clone()`、`Spring` 的 `prototype` 作用域 Bean

---

### 3.2 结构型模式（Structural）

> 关注如何组合类和对象以形成更大的结构。

#### 代理模式 (Proxy)

**核心意图**：为其他对象提供一种代理以控制对这个对象的访问。

**适用场景**：
- 远程代理：访问远程对象（RPC）
- 虚拟代理：延迟创建开销大的对象（图片懒加载）
- 保护代理：控制访问权限
- 智能引用：附加额外操作（引用计数、日志）

**Java 实现**：
- 静态代理：代理类与目标类实现同一接口
- JDK 动态代理：基于接口，`InvocationHandler`
- CGLIB 代理：基于继承，`MethodInterceptor`

**实际应用**：Spring AOP、MyBatis Mapper 接口代理、RPC 框架

**与装饰器的区别**：
- 代理：控制访问，客户端通常不知道代理的存在
- 装饰器：增强功能，客户端通常知道并参与装饰过程

---

#### 装饰器模式 (Decorator)

**核心意图**：动态地给一个对象添加一些额外的职责，就增加功能来说，装饰器模式比生成子类更为灵活。

**适用场景**：
- 在不影响其他对象的情况下，以动态、透明的方式给单个对象添加职责
- 处理那些可以撤销的职责
- 当不能采用继承或继承不实际时（如 final 类）

**Java 实现**：装饰器与被装饰对象实现同一接口，持有被装饰对象的引用

**实际应用**：Java IO 流（`BufferedInputStream` 装饰 `FileInputStream`）、Spring 的 `TransactionAwareCacheDecorator`

**与代理模式的区别**：见上文。

---

#### 适配器模式 (Adapter)

**核心意图**：将一个类的接口转换成客户希望的另外一个接口，使得原本由于接口不兼容而不能一起工作的那些类可以一起工作。

**适用场景**：
- 使用已存在的类，但其接口不符合需求
- 需要创建一个可以复用的类，该类可以与其他不相关的类或不可预见的类协同工作

**Java 实现**：
- 对象适配器（组合）：持有被适配对象，实现目标接口
- 类适配器（继承）：继承被适配类，实现目标接口（Java 中较少用）

**实际应用**：`InputStreamReader`(字节流→字符流)、`Arrays.asList()`、`Spring MVC` 的 `HandlerAdapter`

**与装饰器/代理的区别**：
- 适配器：改变接口以兼容不同
- 装饰器：保持接口，增强功能
- 代理：保持接口，控制访问

---

#### 桥接模式 (Bridge)

**核心意图**：将抽象部分与它的实现部分分离，使它们都可以独立地变化。

**适用场景**：
- 一个类存在两个独立变化的维度，且这两个维度都需要扩展
- 不希望使用继承或继承导致类爆炸

**核心思想**：用组合关系代替继承关系，抽象层和实现层各自独立演化。

**与策略模式的区别**：
- 桥接：强调抽象和实现的分离，二者是多对多关系
- 策略：强调算法的 interchangeable，一般是Context持有单一策略

**实际应用**：JDBC（`DriverManager` 是抽象，`Driver` 是实现）、AWT 的 `Peer` 架构

---

#### 组合模式 (Composite)

**核心意图**：将对象组合成树形结构以表示"部分-整体"的层次结构，使得用户对单个对象和组合对象的使用具有一致性。

**适用场景**：
- 表示对象的部分-整体层次结构
- 希望用户忽略组合对象与单个对象的不同，统一使用所有对象

**关键设计**：透明方式（Leaf 也实现 add/remove 但抛异常）vs 安全方式（Component 不声明 add/remove）

**实际应用**：Java UI 的 `Container`/`Component`、文件系统目录结构、组织架构

---

#### 外观模式 (Facade)

**核心意图**：为子系统中的一组接口提供一个一致的界面，外观模式定义了一个高层接口，这个接口使得这一子系统更加容易使用。

**适用场景**：
- 为复杂子系统提供一个简单接口
- 将子系统与客户端解耦
- 层次化系统中，定义每一层的入口

**与中介者的区别**：
- 外观：简化子系统的使用接口，单向（客户端→外观→子系统）
- 中介者：封装对象间的交互，多向（同事类 ↔ 中介者 ↔ 同事类）

**实际应用**：SLF4J（各种日志框架的外观）、Spring 的 `JdbcTemplate`

---

#### 享元模式 (Flyweight)

**核心意图**：运用共享技术有效地支持大量细粒度的对象。

**适用场景**：
- 系统中有大量相似对象，造成内存开销大
- 对象的大部分状态可以外部化（内部状态 vs 外部状态）

**核心概念**：
- 内部状态（Intrinsic）：不随环境变化，可共享
- 外部状态（Extrinsic）：随环境变化，不可共享

**实际应用**：`Integer.valueOf()`(-128~127 缓存)、`String` 常量池、连接池、线程池

---

### 3.3 行为型模式（Behavioral）

> 关注对象之间的通信和职责分配。

#### 策略模式 (Strategy)

**核心意图**：定义一系列的算法，把它们一个个封装起来，并且使它们可以相互替换。

**适用场景**：
- 多个类只区别在行为不同
- 需要在不同时间使用不同的算法变体
- 算法使用客户不应该知道的数据

**与状态模式的区别**：
- 策略：客户端主动选择策略，策略之间是平等的
- 状态：状态转换由对象内部规则驱动，状态之间存在转移关系

**实际应用**：`Comparator`、Spring 的 `Resource` 策略、支付策略选择

---

#### 观察者模式 (Observer)

**核心意图**：定义对象间的一对多依赖关系，当一个对象的状态发生改变时，所有依赖于它的对象都得到通知并被自动更新。

**适用场景**：
- 一个对象的改变需要同时改变其他对象，且不知道具体有多少对象有待改变
- 需要解耦发布者与订阅者

**Java 实现**：
- JDK: `Observable`/`Observer`（已废弃，不推荐）
- 推荐: 自定义 `Subject`/`Observer` 接口，或使用 Guava `EventBus`、Spring `ApplicationEvent`

**与发布订阅的区别**：
- 观察者：Subject 直接管理 Observer，耦合度相对较高
- 发布订阅：引入事件中心（Broker），发布者与订阅者完全解耦

**实际应用**：Spring `ApplicationListener`、消息队列、事件驱动架构

---

#### 模板方法模式 (Template Method)

**核心意图**：定义一个操作中的算法的骨架，而将一些步骤延迟到子类中。

**适用场景**：
- 一次性实现一个算法的不变部分，将可变部分留给子类
- 子类间公共行为应提取到公共父类中，避免代码重复

**核心机制**：`final` 的模板方法 + `protected abstract` 的钩子方法

**与策略模式的区别**：
- 模板方法：继承骨架，重写部分步骤，算法结构固定
- 策略：组合算法，整体替换，算法结构可变

**实际应用**：`AbstractList`、`JdbcTemplate`、`HttpServlet` 的 `doGet`/`doPost`

---

#### 责任链模式 (Chain of Responsibility)

**核心意图**：使多个对象都有机会处理请求，从而避免请求的发送者和接收者之间的耦合关系。将这些对象连成一条链，并沿着这条链传递请求，直到有一个对象处理它为止。

**适用场景**：
- 有多个对象可以处理一个请求，哪个对象处理由运行时决定
- 在不明确指定接收者的情况下，向多个对象中的一个提交请求
- 可动态指定一组对象处理请求

**实际应用**：Servlet Filter、Netty Pipeline、审批流程、异常处理链

**与装饰器的区别**：
- 装饰器：每个装饰器都处理请求，层层叠加
- 责任链：只有一个处理器处理请求，找到即停止（或继续传递）

---

#### 命令模式 (Command)

**核心意图**：将一个请求封装为一个对象，从而使你可用不同的请求对客户进行参数化；对请求排队或记录请求日志，以及支持可撤销的操作。

**适用场景**：
- 需要将请求调用者和请求接收者解耦
- 需要支持撤销、重做、事务
- 需要将一组操作组合为一个复合命令

**实际应用**：`Runnable`/`Callable`、线程池任务封装、GUI 的 Action、事务管理

**与策略模式的区别**：
- 命令：封装"动作"，关注请求的发送和执行解耦，可撤销
- 策略：封装"算法"，关注算法的 interchangeable

---

#### 迭代器模式 (Iterator)

**核心意图**：提供一种方法顺序访问一个聚合对象中的各个元素，而又不需暴露该对象的内部表示。

**适用场景**：
- 访问聚合对象内容而无需暴露内部表示
- 支持对聚合对象的多种遍历方式
- 为遍历不同的聚合结构提供一个统一的接口

**实际应用**：Java `Iterator` 接口、`Enumeration`、`ListIterator`

---

#### 状态模式 (State)

**核心意图**：允许对象在其内部状态改变时改变它的行为，对象看起来似乎修改了它的类。

**适用场景**：
- 一个对象的行为取决于它的状态，且它必须在运行时刻根据状态改变行为
- 代码中包含大量与对象状态有关的条件语句

**与策略模式的区别**：见策略模式。

**实际应用**：订单状态机、线程状态（`Thread.State`）、电梯/交通灯控制

---

#### 中介者模式 (Mediator)

**核心意图**：用一个中介对象来封装一系列的对象交互。中介者使各对象不需要显式地相互引用，从而使其耦合松散，而且可以独立地改变它们之间的交互。

**适用场景**：
- 一组对象以定义良好但是复杂的方式进行通信
- 一个对象引用很多其他对象并直接与这些对象通信，导致难以复用
- 想定制一个分布在多个类中的行为，而又不想生成太多子类

**与外观模式的区别**：见外观模式。

**实际应用**：MQ（消息中间件）、MVC 的 Controller、聊天室、Spring 的 `ApplicationContext`（作为 Bean 的中介者）

---

#### 备忘录模式 (Memento)

**核心意图**：在不破坏封装性的前提下，捕获一个对象的内部状态，并在该对象之外保存这个状态。这样以后就可将该对象恢复到原先保存的状态。

**适用场景**：
- 需要保存和恢复数据的相关状态场景
- 需要提供一个可回滚的操作

**关键问题**：窄接口（Caretaker 只能看到备忘录外壳）vs 宽接口（Originator 可访问内部状态）

**实际应用**：数据库事务的 savepoint、编辑器撤销/重做、游戏存档

---

#### 解释器模式 (Interpreter)

**核心意图**：给定一个语言，定义它的文法的一种表示，并定义一个解释器，这个解释器使用该表示来解释语言中的句子。

**适用场景**：
- 文法简单（复杂的用语法分析器生成器如 ANTLR）
- 效率不是关键问题

**实际应用**：正则表达式引擎、`java.util.regex.Pattern`、EL 表达式、SQL 解析器（简单场景）

---

#### 访问者模式 (Visitor)

**核心意图**：表示一个作用于某对象结构中的各元素的操作。它使你可以在不改变各元素的类的前提下定义作用于这些元素的新操作。

**适用场景**：
- 对象结构中包含很多类，需要对这些类实施一些不相关的操作
- 需要对一个对象结构中的对象进行很多不同的且不相关的操作，且不想让这些操作"污染"这些类
- 对象结构很少改变，但经常需要在此结构上定义新的操作

**核心机制**：双分派 —— 元素的 `accept(visitor)` + 访问者的 `visit(element)`

**与策略模式的区别**：
- 策略：对单个对象封装算法
- 访问者：对一组对象结构封装操作，可跨类型访问

**实际应用**：ASM 字节码操作、编译器 AST 遍历、报表生成（对异构数据结构）

---

## 四、模式对比速查表

### 4.1 "包装三兄弟"

| 维度 | 代理模式 | 装饰器模式 | 适配器模式 |
|------|----------|-----------|-----------|
| **意图** | 控制访问 | 增强功能 | 接口转换 |
| **接口** | 与目标相同 | 与目标相同 | 与目标不同 |
| **客户端感知** | 通常不知道 | 通常知道 | 只知道目标接口 |
| **核心思想** | 替代目标 | 包装目标 | 转换目标 |
| **典型应用** | AOP、RPC | IO 流 | 格式转换 |

### 4.2 工厂家族

| 维度 | 简单工厂 | 工厂方法 | 抽象工厂 | 建造者 |
|------|----------|----------|----------|--------|
| **创建对象数** | 1 个 | 1 个 | 1 族 | 1 个（复杂） |
| **扩展方式** | 修改工厂类 | 新增工厂子类 | 新增工厂子类 | 新增 Builder |
| **客户端耦合** | 工厂类 | 抽象工厂 | 抽象工厂 | Director |
| **关注点** | 创建什么 | 谁创建 | 创建一族 | 如何一步步创建 |

### 4.3 行为型易混淆模式

| 维度 | 策略 | 状态 | 模板方法 |
|------|------|------|----------|
| **行为变化** | 客户端选择 | 状态自动驱动 | 子类重写 |
| **替换方式** | 运行时替换对象 | 状态对象内部转换 | 编译时确定继承 |
| **算法结构** | 整个算法替换 | 行为随状态变 | 骨架固定，步骤可变 |

| 维度 | 观察者 | 中介者 | 责任链 |
|------|--------|--------|--------|
| **通信方式** | 一对多广播 | 多对多集中转发 | 链式传递 |
| **解耦程度** | Subject 知 Observer | 完全解耦 | 只知下一个节点 |
| **典型场景** | 事件订阅 | 消息队列、聊天室 | 审批、Filter |

## 六、设计模式应用原则

### 6.1 何时使用设计模式

《Head First》：
1. 当设计中出现"坏味道"（重复代码、庞大类、僵化设计）时
2. 当需求变化频繁，需要系统保持灵活时
3. 当需要复用已有设计经验时

《研磨设计模式》：
- 不要过度设计，不是所有地方都需要模式
- 先让代码工作，再考虑模式优化（重构时引入）
- 模式是工具，不是教条

### 6.2 常见反模式

- **模式滥用**：为了用模式而用模式，增加不必要的复杂度
- **模式堆砌**：一个系统中堆砌大量模式，导致理解困难
- **僵化应用**：不考虑上下文，机械套用模式结构
- **忽视简单方案**：简单方案能解决问题时，不要引入模式

### 6.3 重构到模式

《设计模式之禅》强调：设计模式最好的学习方式是在**重构**中体会。
1. 先写出能工作的代码
2. 识别坏味道（长方法、大类、重复、条件泛滥）
3. 应用设计原则分析
4. 引入合适的模式重构
5. 保持测试通过

### 6.4 模式混编

《设计模式之禅》第四部分专门讨论模式混编：
- 命令 + 责任链：实现命令的 undo/redo
- 工厂 + 单例：工厂本身单例，生产的产品也受控
- 观察者 + 中介者：事件总线架构
- 策略 + 工厂：运行时动态选择策略
- 装饰 + 代理：AOP 的层层增强

---

## 七、学习路径建议

《研磨设计模式》推荐的学习路径：

1. **先学原则**：理解 SOLID + LoD + CARP
2. **再学模式**：按创建型 → 结构型 → 行为型的顺序
3. **对比学习**：相似模式放在一起对比（如策略 vs 状态）
4. **源码验证**：在 JDK/Spring 源码中找到模式的实际应用
5. **项目实践**：在实际项目中识别模式应用场景
6. **重构体会**：从烂代码重构到模式，体会"为什么"

《Head First》强调：**理解 WHY 比记住 HOW 重要一万倍。**
